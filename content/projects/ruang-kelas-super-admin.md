# Overview

A web admin console for running the whole Ruang Kelas platform — schools, users, academic data, subscriptions, broadcasts and content moderation — with the clarity a power user needs.

![Super Admin console: dashboard, user management and subscriptions screens.](/images/portfolio/ruang-kelas-super-admin/overview.webp)

## Role & Responsibilities

As the **Product Designer (Web UI/UX)**, I designed the console end to end: information architecture and navigation, the desktop layout system (sidebar, top bar, content), data tables, filters and row actions, detail views and multi-step forms, KPI cards, charts and a status language, a shared component and pattern library, and developer-ready handoff.

The team owned product scope and admin requirements, backend, data and permissions, business and billing logic, and infrastructure and deployment.

## Problem & Goals

One team runs everything — onboarding schools, billing, support, moderation — so the console has to make a broad platform manageable by a small team. A platform admin lives in tables and detail views all day; they need to find, filter, act and trust the data fast, without hunting.

**Goal:** Give many different domains one predictable shell — sidebar, tables, filters, detail views and forms — so every new area feels already familiar.

**How might we** let a small admin team manage schools, users, billing, content and settings from one console that stays clear no matter how dense the data gets?

## Process & Design Decisions

Information architecture first — one sidebar, thirteen domains, grouped into two lanes (day-to-day platform work and the system tools beneath), each following a list → detail → action pattern. Then the desktop layout system, data tables, filters and row actions, detail views and multi-step forms, KPI cards, charts and status language, a shared pattern library, and developer handoff.

Four key UX decisions:

1. **One shell, thirteen domains** — a persistent sidebar, top bar and repeated list → filter → detail → action pattern reused everywhere.
2. **Tables that stay readable when dense** — an identity column with avatar and sub-label, colour-coded status chips, right-aligned actions, and filters above every list.
3. **Decisions surfaced where you act** — report reason, category, status and quick actions inline, with a full detail view one click away.
4. **A console that explains itself** — KPI cards, trend charts, a live activity feed and a system-status panel answer “how's the platform?” on the first screen.

![Onboarding a school: browse schools, add a school, school detail.](/images/portfolio/ruang-kelas-super-admin/process.webp)

## Solution Highlights

One coherent console across thirteen admin domains, designed so a small team can run the whole platform. Dense tables are designed to remain scannable and actionable at thousands of records. Judgment calls — moderation and subscription changes — are supported by context shown inline. Platform health and momentum are readable at a glance, with detail one click deeper. A reusable pattern and component library supports consistency across domains.

![Four console screens: one shell, dense tables, inline decisions, and a self-explaining console.](/images/portfolio/ruang-kelas-super-admin/solution.webp)

### Adaptive Desktop Shell

The desktop console supports both expanded and collapsed sidebar layouts. This is an **adaptive desktop shell**, not a claim that the admin console was designed as a mobile application.

![Super Admin console with the sidebar expanded and collapsed.](/images/portfolio/ruang-kelas-super-admin/responsive.webp)

## Outcomes & Lessons (Qualitative)

This is a qualitative project. The outcomes below describe design intent, clarity, consistency and handoff, **not independently measured usability or operational results**.

The design establishes a consistent console across thirteen domains, with scannable tables, contextual actions and at-a-glance platform status. A shared pattern and component library helps keep workflows coherent and supports developer-ready handoff as the product grows.

**Lesson:** Good admin design disappears — the work it enables doesn't. A shared shell, honest tables and a consistent status language are what let a broad, data-heavy product stay usable as it grows.

## Scope & Disclaimer

Ruang Kelas is a school platform; the Super Admin console shown here uses sample data (example schools, users and transactions). This case study covers the web UI/UX contribution and excludes the product's backend, permissions and business logic.
